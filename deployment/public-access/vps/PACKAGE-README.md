# Optional permanent numeric-IP gateway

This configuration is prepared deployment support. No actual VPS IP, account,
SSH connection, nginx execution, reboot recovery or certificate issuance is
claimed by this release. A new deployment needs an authorized VPS, public IPv4,
installed nginx/OpenSSH/systemd, setup access and a verified SSH identity.
An outbound VPN address is not a substitute for an inbound VPS gateway.

The Windows server connects outward using SSH. VPS nginx forwards approved
requests through VPS loopback `127.0.0.1:18080` to the Windows public gateway at
`127.0.0.1:18734`. Private Apache, database and model-management listeners are
never forwarded. The Windows public allowlist remains authoritative.

Copy `target.example.json` to `target.json` and supply an actual authorized host,
dedicated unprivileged username, private-key path and independently verified
known-host file. Do not copy the SSH private key to the VPS. Verify its host key
using the provider console or an established authenticated channel; a key scan
alone does not establish trust. Add the actual VPS public IP to the Windows
gateway configuration's `vps_public_ips` list.

From PowerShell 7 in the extracted gateway folder, validation is local by default:

```powershell
& .\scripts\Start-DragonVpsTunnel.ps1
& .\scripts\Register-DragonVpsTunnelTask.ps1
```

Missing configuration produces `requires_configuration` without a connection.
With validated configuration, use `Start-DragonVpsTunnel.ps1 -Connect`. It uses
strict host-key verification, noninteractive key authentication, forward-bind
failure detection and bounded keepalives. `Register-DragonVpsTunnelTask.ps1 -Install`
registers a native boot task without starting it. The LOCAL SERVICE identity needs
exact read access to its configuration, key and known-host files and a headless
usable key. No broad ACL grants or keys are generated by that script. Only one
supervisor is configured, with three bounded restarts and no overlapping instances.

On the actual authorized VPS, copy this package directory and a public SSH key.
The native apply script requires the existing nginx and sshd include directories;
it does not install packages, change a firewall or replace unrelated site files.
Its default is a dry run:

```sh
bash vps/install-gateway.sh --ip ACTUAL_VPS_PUBLIC_IPV4 --public-key-file /secure/tunnel.pub
sudo bash vps/install-gateway.sh --ip ACTUAL_VPS_PUBLIC_IPV4 --public-key-file /secure/tunnel.pub --apply
```

Review the rendered files first. Apply only on the authorized VPS. The script
requires root for mutation, creates a dedicated forwarding account, backs up only
marked DRAGONHYDRA configuration, runs full `nginx -t` and `sshd -t`, verifies
effective forwarding restrictions and rolls back its owned files on failure.
Existing incompatible default-server configuration must be resolved explicitly;
the script will not silently remove another site's configuration.

The HTTP baseline serves `http://ACTUAL_VPS_PUBLIC_IPV4/` without a domain or TLS
redirect. It exposes only the public Joomla frontend, public viewer and allowed
read APIs. Optional HTTPS uses `vps-nginx-https-ip.conf.example`; enable it only
after obtaining a trusted certificate whose IP SAN contains the actual address.
The baseline's ACME webroot is served on the VPS without proxying through Windows.

Current [Let's Encrypt IP certificate instructions](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)
describe Certbot 5.4+ webroot support and short-lived certificates. On the actual
VPS, verify the installed version and staging challenge reachability first:

```sh
sudo certbot certonly --staging --preferred-profile shortlived --webroot \
  --webroot-path /var/lib/dragonhydra/acme --ip-address ACTUAL_VPS_PUBLIC_IPV4 \
  --cert-name dragonhydra-ip
```

After staging works, request a trusted production certificate, inspect its SAN,
configure the TLS paths and verify automated renewal with a deployment hook that
validates and reloads nginx. Also verify that nginx and the target SSH service are
enabled for boot on the selected distribution. These are required deployment
checks, not release test results.

Validate externally from an unrelated network: numeric-IP homepage/assets, a real
canonical match, API reads, blocked private routes, rejected mutations, an origin
outage, SSH reconnection, service restart and VPS reboot. Keep an existing trusted
administrative SSH recovery session while validating configuration. Record the
actual IP, OS, installed versions, commands, results and certificate-renewal proof.
